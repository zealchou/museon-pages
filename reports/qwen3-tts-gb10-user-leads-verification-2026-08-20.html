Qwen3-TTS／GB10 新線索查證報告

查證日期：2026-08-20（Asia/Taipei）｜範圍：使用者提供之 Faster-Qwen3-TTS、CUDA Graph、Mamba 依賴、Unsloth NVFP4 與 GGUF 主張

結論先說：這批線索並非全假；NVIDIA 論壇文、社群專案、ARM64 Docker image 與 llama.cpp 的 Qwen3-TTS GGUF 支援都真實存在。但它們不能直接轉成「現在就安裝」的指令：3 倍與「全部 CUDA Graph」被誇大，Mamba/causal_conv1d 的依賴主張錯置，Unsloth NVFP4 沒有 Qwen3-TTS 的官方支援證據。唯一可作為後續候選實驗的是獨立的 Faster-Qwen3-TTS Docker 路線；它不是現有官方 qwen_tts.Qwen3TTSModel.generate_voice_clone() 的原地加速。

決策：現在不要依這批文字安裝 Unsloth、NVFP4、Mamba 或 causal_conv1d；也不要把 GGUF 當成既有 Python API 的量化替換。若之後要測 Faster-Qwen3-TTS，應把它當作隔離的替代服務／benchmark 實驗，先固定 image digest、同一句料與官方 baseline 做 AB 測試；本次工作單不執行安裝。

1. NVIDIA 論壇、專案與 Docker image 是否真實？

真實存在指定的 NVIDIA Developer Forums 貼文可正常開啟。它是帳號 martinB78 發在 DGX Spark/GB10 社群板的部署 playbook，目的為把 upstream Faster-Qwen3-TTS 包成 4 個 OpenAI-compatible HTTP 服務：VoiceClone（8020）、VoiceDesign（8021）、CustomVoice（8022）與 streaming VoiceClone（8023）。這是 NVIDIA 託管的論壇，不代表 NVIDIA 對作者程式碼、效能或相容性背書。

貼文與其 GitHub repo均連得到 mARTin-B78/dgx-spark-faster-qwen3-tts。repo 的定位是「DGX Spark fixes plus packaging」：Dockerfile 基於 CUDA 13.0.2，安裝 PyTorch cu130 wheel，然後 clone upstream andimarafioti/faster-qwen3-tts 並套一個 server patch；它不是 Qwen 官方分支，也不是為 sm_121 新寫／編譯的自訂 CUDA kernel 分支。

Docker image 亦存在Docker Hub repository可開啟，tag metadata 顯示 ARM64 image；repo 文件列出 martinb78/faster-qwen3-tts-dgx-spark:latest（三種非 streaming 模式）與 :latest-streaming。論壇早期寫的 v4 與另一個 streaming repo/tag 已被後續內容調整，故原始貼文中的 image 名稱不是穩定介面，不能照舊字串盲拉。

重要的是，該 repo 自己寫明「Flash Attention on SM 121 – avoided; uses CUDA graphs instead」。所以這條線索沒有推翻「暫時不要安裝 flash-attn」這個既有結論；它選的是避開 FlashAttention 的另一條路。

2. CUDA Graph 與「3 倍」是否有 benchmark？

有作者發布的具體 benchmark，非純口號；但不是獨立驗證，也不是 3×。Upstream README 的「Results」表列出 1.7B、DGX Spark（GB10）一組數字：baseline RTF 1.01、TTFA 661 ms；CUDA Graph RTF 1.87、TTFA 400 ms，表中速度差為 1.9× RTF / 1.7× TTFA。0.6B 的同硬體數字是 2.2× / 2.0×。測量方法寫明包含 tokenization 與 inference，RTF 是音訊秒數／生成秒數，TTFA 使用 streaming、chunk_size=8；repo 也提供 benchmark.sh。

因此，「加速存在」有可重跑的作者級佐證；但「3 倍」在 GB10 1.7B 的公開表格中不成立。更不能把其他硬體（例如 RTX 4090）的 5× 數字移植成 GB10 結論。已查資料也未提供 GB10 的原始 JSON、driver 版本、PyTorch exact build、完整測試語料或第三方重現結果；可信度應定為待本機 AB 重跑的社群 benchmark，不是採購／生產保證。

「完全編譯為 CUDA Graph」的程式碼核對

此句不符合程式碼。上游 talker_graph.py 明確只 capture「single-token decode step」；predictor_graph.py capture code predictor 的 15-step loop。相反地，streaming.py 明說可變長 PREFILL「still uses HF forward」，而 model.py 在 graph loop 以外呼叫 speech_tokenizer.decode(...) 產生 waveform。更精確的說法是：它以 StaticCache + torch.cuda.CUDAGraph 降低 autoregressive decode 的 Python/kernel-launch overhead；不是把完整文本前處理與音訊解碼「完全編譯」成一張 CUDA Graph。

3. Qwen3-TTS-12Hz-1.7B-Base 是否依賴 Mamba？

否。Qwen 官方 pyproject.toml 的 runtime dependencies 是 transformers==4.57.3、accelerate、gradio、librosa、torchaudio、soundfile、sox、onnxruntime、einops；其中沒有 mamba-ssm 或 causal-conv1d。

再讀官方 modeling_qwen3_tts.py 可見 Talker 是 self-attention、RoPE、MLP、RMSNorm 的 Transformer；12Hz tokenizer 檔使用的是原生 torch.nn.Conv1d／ConvTranspose1d 與其自家 Qwen3TTSTokenizerV2CausalConvNet 類別。名稱帶 CausalConvNet 不等於外部 causal-conv1d extension；整個官方 tree 對 mamba、causal_conv1d 都沒有匯入。原文把「某些 Mamba/SSM 模型常見的外掛」張冠李戴到 Qwen3-TTS。

所以在既有的官方 generate_voice_clone() 環境上，為了「避免慢速 Python fallback」去手動編譯這兩個 package 沒有依據，也不能合理預期會加速。

4. Unsloth NVFP4、GGUF 是否明確支援這個 TTS 模型？

Unsloth NVFP4

沒有。Unsloth 的 Qwen3 公告說的是 2025 年的 Qwen3 文字 LLM、微調與其 Qwen3 GGUF；它沒有把 Qwen3-TTS 列為支援模型。更直接的反證是 Unsloth 官方 GitHub 的 issue #3951：它是「Add FT support for the Qwen3-TTS model」的公開 feature request，狀態仍為 Open，標籤為「pending on roadmap」與「help wanted」，沒有關聯 PR。這至少排除「Unsloth 已明確支援 Qwen3-TTS NVFP4」這個說法。

GGUF／llama.cpp

有支援，但不是 Qwen 官方 Python 套件的格式支援。llama.cpp PR #26254 已於 2026-08-04 merge；它明列 Qwen3-TTS Base，支援 --tts-speaker-file，並示範下載 ggml-org/Qwen3-TTS-12Hz-1.7B-Base-GGUF。目前 llama.cpp TTS README 也保留同一組 voice-cloning 用法。

這表示「Qwen3-TTS 可以透過 GGUF／llama.cpp 做 TTS、且含 reference audio」是可查證的；但它需要換成 llama-tts runtime 與 GGUF model/mmproj 資產，不能丟進 Qwen3TTSModel.from_pretrained() 或沿用 generate_voice_clone()。使用者貼的 Reddit 關於 Qwen3 27B 的 GGUF、speculative decoding、CUDA graphs 是文字 LLM 個案，並未證明 Qwen3-TTS-1.7B Base 在 DGX Spark 的吞吐量或品質，故不能用作這個 TTS 工作負載的證據。

5. 最終分類與可行決策

分類內容
真實可查NVIDIA forum 貼文、mARTin-B78 repo、ARM64 Docker images；Faster-Qwen3-TTS 的 CUDA Graph decode；llama.cpp 已合併 Qwen3-TTS GGUF / voice clone 支援。
有條件可查Faster-Qwen3-TTS 作者發布 GB10 benchmark（1.7B 約 1.9× RTF）；有測試腳本與定義，但沒有本機／第三方重現證據，且適用的是替代 API/service 路線。
不實或誤導「全部文本與音訊都編譯進 CUDA Graph」、「GB10 3×」；Qwen3-TTS 依賴 Mamba/causal_conv1d；Unsloth NVFP4 已支援 Qwen3-TTS；拿 Qwen3 LLM 的 GGUF Reddit 數字當作 TTS 成效。

現在能不能照這批資訊裝東西？不能。尤其不能裝 Unsloth/NVFP4、mamba-ssm、causal-conv1d，也不能因這些文字恢復安裝 FlashAttention。未來若要探索加速，唯一資訊量足夠的候選是 mARTin/upstream Faster-Qwen3-TTS；但它必須是新的、隔離的 Docker API 實驗，且須以現有官方環境做 baseline，固定模型、reference audio/transcript、輸入文本、dtype、warmup、版本與 image digest，並同時比較 RTF、TTFA、聲音品質／克隆相似度與輸出錯誤率。AB 結果出來之前，不應替換目前批次管線。
