NVIDIA NVFP 格式與 GB10 自行量化可行性查證

日期：2026-08-30（Asia/Taipei）
範圍：只查 NVIDIA／OCP／工具維護者的一手文件與官方原始碼；不安裝工具、不下載權重、不實測量化。

1. 【結論】

截至本次查證，NVIDIA 正式命名且發布的是 NVFP4；沒有找到 NVIDIA 正式格式名稱 NVFP6 或 NVFP8。 使用者很可能把 Blackwell 硬體的「FP6 支援」、OCP 的 MXFP6／MXFP8，或一般 FP8（E4M3／E5M2），混成了「NVFP6／NVFP8」。

這台 GB10 理論上能自行把 27B 級 Hugging Face 模型做成 NVFP4。 原因是它是 Blackwell、compute capability 12.1、ARM64（aarch64/SBSA）、119.7 GiB 統一記憶體；這同時符合 NVIDIA Model Optimizer 的 Linux/aarch64、CUDA 12/13 與 NVFP4 Blackwell 部署條件。實際開跑前仍須確認安裝中的 CUDA toolkit、PyTorch、ModelOpt/容器與推論 runtime 版本相容，並停止或限縮其他吃統一記憶體的模型服務。

「NVFP6／NVFP8」不是把 NVFP4 的 bit 數從 4 改成 6/8 就能得到的同一格式：NVFP4 的縮放規則（16 值一組、FP8 E4M3 區塊 scale、再加每 tensor FP32 scale）是該格式定義的一部分。

2. 【格式家族全貌】

名稱 是否為正式名稱／誰定義 元素與縮放方式 與 NVFP4 的關係與實務判讀
NVFP4 是。NVIDIA 為 Blackwell 引入的正式名稱。 元素為 FP4 E2M1；每 16 個值共用一個 FP8 E4M3 scale，另有每 tensor 的 FP32 第二層 scale；有效約 4.5 bits/value。 NVIDIA 自家的 FP4 格式。Model Optimizer 的 nvfp4 是主要 DIY PTQ 路徑；官方明說部署的 NVFP4 inference 需要 Blackwell 與 TensorRT-LLM 1.2+。 NVIDIA 技術說明；ModelOpt 支援矩陣
MXFP4 是。OCP MX v1.0 公開標準。 FP4 E2M1；每 32 個值共用一個 E8M0（純 2 的冪）scale。 與 NVFP4 都是 block/microscaling FP4，但不是同一個二進位格式、縮放規格或 checkpoint 格式。Blackwell 可支援兩者；ModelOpt 文件也將 mxfp4_mlp_weight_only 與 NVFP4 分開。 OCP MX 規格；NVIDIA 比較表
MXFP6 是。OCP MX v1.0 公開標準。 6-bit 元素有 E3M2、E2M3 兩種；32 值一組 E8M0 scale。 這是最可能被誤叫成「NVFP6」的東西。它是 MX/OCP 格式，不是 NVIDIA 已發布的 NVFP6。Blackwell 的確支援 FP6／MX block-scaled 路徑，但截至查閱日，ModelOpt 的公開 PTQ recipe 清單沒有 nvfp6 或 mxfp6 一般使用者入口；不能把硬體支援直接等同於成熟的 DIY 量化＋推論工作流。 OCP MX 規格；NVIDIA FP8/Blackwell 說明；ModelOpt recipes
MXFP8 是。OCP MX v1.0 公開標準。 FP8 E4M3 或 E5M2 變體；32 值一組 E8M0 scale。 是 OCP microscaling 的 8-bit 成員，並非 NVFP4 的「8-bit 版」。ModelOpt、Transformer Engine、LLM Compressor 都以 MXFP8 明確稱呼它。 OCP MX 規格；Transformer Engine
FP8（一般 FP8） 是。業界通用名稱；NVIDIA Hopper/Transformer Engine 明列 E4M3、E5M2。 E4M3 偏精度、E5M2 偏動態範圍；「一般 FP8」常採每 tensor FP32 scale，與 MX 的 block scale 不同。 不應稱作 NVFP8。 NVIDIA 官方文件把它叫 FP8，並把 NVFP4、MXFP8 分開列出。NVFP4 內部雖用 FP8 E4M3 當區塊 scale，但那不會使 FP8 變成 NVFP8。 NVIDIA Transformer Engine FP8 primer

命名的可驗證結論

  1. NVIDIA 的 NVFP4 官方文章把 Blackwell 的三種主要 4-bit 格式列成 FP4、MXFP4、NVFP4；並沒有列出 NVFP6 或 NVFP8。 官方表 1
  2. OCP 的 MX v1.0 明確列出 MXFP8、MXFP6、MXFP4；OCP 也確認 NVIDIA 是共同制定者之一。這可解釋為何常在 NVIDIA/Blackwell 文章裡看見 MX 名稱，但它仍是開放的 OCP 家族。 OCP 規格；OCP 公告
  3. 本次在 NVIDIA Developer、NVIDIA Docs、NVIDIA/Model-Optimizer、Transformer Engine 與 CUTLASS 的正式文件中，以精確字串搜尋 NVFP6、NVFP8，沒有找到把它們定義成 NVIDIA 資料格式的條目；相對地，這些文件直接使用 NVFP4、MXFP4/6/8、FP8。這是有範圍的否定結論：它足以支持「不要把 NVFP6/NVFP8 當成目前正式產品格式」，但不能用來預言未來 NVIDIA 不會取這種名字。

3. 【自己量化需要什麼】

首選工具：NVIDIA Model Optimizer（原 TensorRT Model Optimizer）

這是 NVIDIA 官方直接推薦的 NVFP4 路徑。它可做 post-training quantization（PTQ），也可在需要品質補救時走 quantization-aware training（QAT）。Hugging Face PTQ 範例提供 nvfp4／nvfp4_mlp_only／nvfp4_experts_only／nvfp4_omlp_only presets，輸出 Unified Hugging Face checkpoint，可供 TensorRT-LLM、vLLM 或 SGLang 使用。 官方 README 與 PTQ 範例

建議流程如下：

  1. 準備原始 Hugging Face BF16/FP16 checkpoint、足夠磁碟與一個隔離 Python/container 環境。
  2. 使用 NVIDIA 建議的 TensorRT-LLM container，或 Linux 上安裝 nvidia-modelopt[hf] 加範例 requirements。 安裝文件
  3. 選 recipe：若追求最大壓縮，為完整 W4A4 的 nvfp4_default；若先追求可用性／品質，NVIDIA 建議 dense 27B 優先試 nvfp4_mlp_only 或 nvfp4_omlp_only，讓敏感的 attention QKV 留在高精度。 recipe 說明
  4. 跑 calibration forward pass，量測 activation 範圍、決定 scale，然後 export checkpoint。官方範例的典型 calibration 是 128–512 samples，預設資料混用 cnn_dailymail 與 nemotron-post-training-dataset-v2；若模型用在特定語言、長上下文、工具呼叫或多模態，應以代表該用途的資料覆蓋校準與後續品質驗收。 官方 PTQ 說明
  5. 用目標 runtime 載入，做輸出品質、長度、工具格式及目標負載的測試；量化成功只代表檔案產生，不代表特定模型／特定 runtime 的品質已驗收。

官方簡化 API 是 mtq.quantize(model, mtq.NVFP4_DEFAULT_CFG, forward_loop)；實務上用其 hf_ptq.py 或 YAML recipe 比較容易重現。 API 範例

可用替代：LLM Compressor（vLLM Project）

llmcompressor 是 vLLM Project 維護的另一條 PTQ 路徑，輸出 compressed-tensors checkpoint，公開列出 NVFP4、MXFP4、MXFP8 與 calibration／disk offloading 支援。其文件把 NVFP4 定義為 group-size 16、FP8 scale，並寫明 W4A4 NVFP4 要用 calibration dataset；支援目標是 Blackwell SM100+。 LLM Compressor README；compression schemes

它是有效的替代，不是 NVIDIA 官方的主文件路徑；最重要的取捨是輸出 checkpoint 格式與 runtime 相容性。若現有服務已穩定吃 ModelOpt MIXED_PRECISION 格式，優先用 ModelOpt；若部署明確走 vLLM/compressed-tensors，LLM Compressor 值得比較。無論哪一條，MXFP6 目前都不是兩者公開文件中「一般團隊一條命令可量化」的同等成熟選項。

軟硬體需求，以及舊卡能否做

項目 官方可確認的要求／界線
OS／CPU 架構 Model Optimizer Linux 支援 x86_64、aarch64（SBSA）；所以 ARM64 本身不是阻礙。
Python／CUDA／PyTorch ModelOpt 目前列 Python >=3.10,<3.15、CUDA 12.x 或 13.x、PyTorch >=2.8；TensorRT-LLM >=1.0 與 TensorRT >=10.0 是選配／部署相關。 安裝文件
產檔時的加速 ModelOpt 的 NVFP4 Triton accelerated kernels 要 compute capability >= 8.9；不符合時，文件沒有說格式無法表示，但不具備這條加速路徑。其 Changelog 也記錄某些 NVFP4 scale search 會在 CPU/Triton 不可用時 fallback。 安裝文件；Changelog
官方支援的 NVFP4 推論 ModelOpt 支援矩陣明確寫 NVFP4 inference requires Blackwell GPUs and TensorRT-LLM v1.2+。這是「部署加速／正式支援」要求，不等價於「任何舊卡絕不可能算出一份檔案」。 支援矩陣註腳

因此嚴格回答是：Blackwell 是 NVFP4 的官方硬體推論目標；官方文件沒有把「正確產生 NVFP4 checkpoint」寫成 Blackwell-only 的硬門檻。 舊 GPU 可能可跑部分 PTQ/CPU fallback，卻沒有原生 NVFP4 Tensor Core 推論，且相容性與速度不是本報告建議承諾的路徑。若目標是「產出後就在本機高效使用」，應在 Blackwell 上做。

記憶體、磁碟與大概工時

以下先把可精算的靜態容量和不能由參數數量精算的峰值分開：

項目 27B 的計算／證據 意義
原始 BF16 權重下限 27e9 × 2 bytes = 54.0 GB decimal = 50.3 GiB。 這只是權重本體；不含 tokenizer、視覺塔、暫存、Python/PyTorch、activations。
全模型 NVFP4 的理想權重下限 NVFP4 為 4-bit value + 每 16 值 8-bit scale = 4.5 bits/value；27e9 × 4.5/8 = 15.19 GB decimal = 14.14 GiB，另有 per-tensor FP32 scale。 實際檔會較大：常會留 lm_head、embeddings、norm、vision/MTP 或 attention 的一部分在 BF16/FP8。
磁碟下限（原檔 + 理想量化輸出） 約 69.19 GB decimal = 64.45 GiB，未含下載快取、暫存與保留兩份輸出。 建議實務上預留遠高於此數字的空間，而不是邊量邊清原檔。
PTQ 峰值統一記憶體 沒有 NVIDIA 公開的「Qwen3.8-27B on GB10」峰值數字。 除了原始權重，峰值受 calibration 的 batch/seq length、attention、模型實作、是否寫出輸出、是否有其他服務佔用所影響。ModelOpt 提供 --low_memory_mode（僅 FP8/NVFP4 + max calibration）與 sequential device map 來降低需要量。 官方說明 不能把 14.14 GiB 量化檔大小誤當成量化過程的所需記憶體。
可比工時證據 NVIDIA 的 Jetson AI Lab 官方教學，在 Jetson Thor T5000 對 Qwen3.6-27B、base weights 已 cache、calib_size=512 的 NVFP4 PTQ 報告 「just over 14 minutes」，export 92 秒。 NVIDIA 官方教學 這是同級 27B 的有價值參考，不是 GB10 benchmark；不可直接承諾 GB10 也是 14 分鐘。ModelOpt 第一次使用還可能先編譯 kernels，官方說可能花幾分鐘。

實務排程可把「原始權重已在本機、先小校準驗通」視為首輪前提，預留至少數十分鐘的維護視窗；若用較長 8K/32K 校準序列、MSE/local-Hessian recipe、品質評測或遇到 ARM64 wheel／runtime 編譯問題，時間會顯著增加。這是保守作業建議，不是 NVIDIA 對 GB10 的速度承諾。

4. 【這台機器的可行性判斷】

使用者提供的條件：GB10 / DGX Spark、ARM64、統一記憶體 119.7 GiB、compute capability 12.1、driver 580.159.03。

比對項目 判定 依據與限制
Blackwell / NVFP4 tensor core 通過 NVIDIA 將 DGX Spark 明定為 GB10 Grace Blackwell、第五代 Tensor Cores、FP4 支援。 DGX Spark 硬體文件
目標 GPU 架構 通過 ModelOpt 對 NVFP4 inference 的正式要求是 Blackwell；GB10 就是 Blackwell。 ModelOpt 支援矩陣
compute capability 通過 使用者的 12.1 高於 ModelOpt NVFP4 Triton acceleration 所需 >=8.9；NVIDIA 的 TensorRT for RTX 文件也明指 GB10 是 compute capability 12.1。 ModelOpt 安裝文件；NVIDIA TensorRT 文件
ARM64/aarch64 通過（理論） ModelOpt Linux 支援表明列 aarch64 (SBSA)。這不能自動保證每個第三方 wheel 都有 ARM64 build，因此優先採 NVIDIA 的 TensorRT-LLM container。 安裝文件
CUDA / driver 大致通過，須以實際 toolkit 確認 ModelOpt 要 CUDA 12.x/13.x。NVIDIA DGX Spark 目前 release notes 列 driver 580.159.03、CUDA Toolkit 13.0.2；使用者的 driver 正相同。不過「compute capability 12.1」不是 toolkit 版本，仍需在真的要開跑時檢查容器/host 的 torch.version.cuda 與 CUDA ABI。 DGX Spark release notes
119.7 GiB 統一記憶體 可行但要控管 單看 27B BF16 權重下限 50.3 GiB，名義上尚有約 69.4 GiB；但那不是可自由使用的 VRAM，OS、桌面、其他 container／vLLM、calibration activation 與 allocator 都在同一池。量化時應先停止既有大型服務，先用短 sequence / 小 calibration 驗通，必要時用 --low_memory_mode。NVIDIA 的產品規格為 128 GB coherent unified memory，與使用者目前可見的 119.7 GiB 不矛盾（後者是可用量）。 DGX Spark 規格
27B 模型整體結論 可做，建議先做小規模驗證再跑正式 PTQ 硬體規格不是阻礙；最大的風險是實際模型架構（vision/MTP/remote code）、所選 runtime 版本、校準長度及統一記憶體爭用。這些不能從「27B」單一數字推導。

建議的低風險啟動順序（尚未執行）

  1. 以 NVIDIA TensorRT-LLM 的 aarch64/SBSA 相容版本建立獨立 container/venv，核對 Python、torch.version.cuda、GPU 名稱及 capability。
  2. 先用 ModelOpt 的一個短 calibration、短 context 的 NVFP4 recipe 驗證：模型能載入、能 export、目標 vLLM/TRT-LLM 能讀回。
  3. 再選擇代表真實工作負載的 128–512 sample calibration；若品質優先，從 nvfp4_mlp_only／nvfp4_omlp_only 開始，而非直接全模型 W4A4。
  4. 對 BF16 基線與 NVFP4 結果至少比較：固定題集、工具/JSON 格式、中文、長輸入、推理與實際 serving；若失真，再調整 recipe 或以 FP8/BF16 保留敏感模組。

5. 【沒查到的部分】

  • 沒有查到 NVIDIA 對「Qwen3.8-27B 在 GB10 用 ModelOpt 量 NVFP4」的官方峰值記憶體、tokens/s 或完工時間。報告只引用 Qwen3.6-27B 在 Jetson Thor T5000 的官方 14 分鐘案例，沒有把它冒充成 GB10 成績。
  • 沒有查到 NVIDIA 正式發布或定義名為 NVFP6、NVFP8 的格式規格、ModelOpt config、Transformer Engine recipe 或產品支援表。這份否定結論的搜尋範圍是 NVIDIA Developer/Docs、NVIDIA/Model-Optimizer、Transformer Engine、CUTLASS 與 OCP MX 文件；在此範圍中精確名稱命中數為 0。未宣稱能預測未來命名。
  • 沒有查到 一條與 NVFP4 一樣成熟、由 ModelOpt/LLM Compressor 公開主推的一般 MXFP6 PTQ + 推論指令。MXFP6 作為 OCP 格式存在，Blackwell/CUTLASS 也可提及相應 block-scaled primitive，但標準存在不等於一般團隊已有端到端部署保證。
  • 本報告沒有實測目前這台機器的可用 RAM、已佔用的 unified memory、磁碟餘量、已裝 PyTorch/CUDA 版本、目標模型授權、或目標 runtime 對特定 Qwen3.8 checkpoint 的相容性；因此「可行」是依官方需求與使用者提供規格作出的理論判定，不是已完成量化的宣稱。
