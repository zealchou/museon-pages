投影片＋既有錄音：講課影片開源方案研究

投影片＋既有錄音＋講稿：自動合成講課影片的開源可行方案

研究日期：2026-08-16。本文只列出已在 GitHub 實際核對過的專案；star 數與最後 push 日期均為本日查 GitHub API 的近似快照，會隨時間變動。

先講結論

有可行方案，但目前沒有一個成熟、完全不懂技術的人只要丟入「任意 PPT/PDF＋一段長錄音＋逐字稿」就能可靠地自動判斷每一張該何時翻頁、再輸出漂亮課程影片的開源一鍵工具。

最穩的實務做法是把問題拆成兩段：

  1. 先取得每張投影片的停留時間（最理想是每頁各一段錄音；否則要用講稿或播放器人工標出切頁時間）。
  2. 以投影片畫面＋這些時間合成 MP4，再用語音辨識產生與校正字幕。

若目前只有「一整段」錄音，逐字稿能幫忙校稿，但不會憑空告訴系統哪一句正好切到第幾頁。除非講稿本來就有每頁標記／時間碼，仍需人工確認切頁點；這是整個流程最常被低估的工作。

1. 技術路線總覽

路線 輸入 → 輸出 難度與適用情境
A. 靜態投影片＋既有音軌合成 每頁投影片圖檔／PDF 頁面＋每頁音檔或切頁時間表 → 投影片依時長停留的 MP4 最務實、畫面最可控；「全自動」的前提是已有每頁音訊或時間表。
B. 字幕自動對時與燒錄 已有錄音或合成好的影片＋講稿 → SRT/VTT 字幕，或直接帶字幕的影片 對本案價值最高的加強項；可自動起稿，但人要快速校對專有名詞與切行。
C. 投影片旁加虛擬講者／數位人 既有錄音＋一張肖像或一段講者正面影片（部分工具還要動作驅動影片）→ 會動嘴的講者畫面，再與投影片合成 效果加分、但硬體與素材要求最高；不是本案的必要第一步。
D. 免寫程式的 GUI／錄製工作流 投影片、錄音、可選字幕 → 在時間軸或螢幕錄製介面手動完成 MP4 自動化較少，卻最適合非工程師：可預覽、拖曳修正、避免腳本失敗。PowerPoint 的「錄製／匯出影片」也屬此類，但不是開源 repo。

2. 可用的 GitHub 專案與工具

路線 A：靜態投影片＋既有音軌合成

這一類的核心不是 AI，而是可靠地把「第 N 張畫面要顯示多久」和音訊拼成影片。PDF／Keynote 通常先轉為一頁一張圖；含動畫的 PPT 則應先在 PowerPoint／Keynote 輸出成影片，否則動畫大多會消失。

Repo 功能與本案適合度 規模與活躍度（2026-08-16 查） 付費 API／本地性 非工程師友善度
FFmpeg/FFmpeg 影音處理底座；可把每張投影片做成定長影片片段、接上既有音檔、加入轉場與字幕。它是最可靠的「引擎」，但不是課程影片專用 App。 約 6.3 萬 stars；2026-08-15 仍有 push，極活躍。 可完全本地；本體主要 LGPL，若選用 GPL 元件／編碼器要另查授權。 低：主要是命令列，通常需工程師或包裝成一鍵流程。
remotion-dev/remotion 用 React 排版與輸出影片；很適合把固定投影片、音軌、字幕與角落講者畫面做成可重複使用的模板。 約 5.6 萬 stars；2026-08-16 仍有 push，活躍。 本地渲染可行；非單純 OSI 開源授權：個人、非營利與小型公司可免費，達條件的公司需公司授權，商用前應看其現行 License。 低：需 JavaScript／React；適合請人做一次模板，之後由表單填素材。
Zulko/moviepy Python 影片合成函式庫，可把圖片、已有音檔、文字與字幕逐段組成 MP4；比 FFmpeg 容易客製，但慢一些。 約 1.5 萬 stars；2026-08-11 有 push；v2 已發布且仍維護。 MIT、可全本地；通常透過 FFmpeg 編碼。 低：需要 Python 程式；適合作為客製小工具的底層。
DH-Center-Tuebingen/ppt2video 真正的「PPT → 圖片 → 音訊 → 影片」小型範例。原設計從投影片備註做 TTS，不是直接吃既有錄音；可當流程參考，需改造才能符合本案。 2 stars、僅 6 commits；最後 push 2025-03。存在且可讀，但不應當成 2026 仍活躍的正式產品。 Windows、已安裝 PowerPoint、FFmpeg；Azure Speech 模式需訂閱／API key，既有語音的情境可避開。 低：Python 腳本，且僅 Windows。

判讀：若有工程協助，FFmpeg 或 Remotion 是長期可重複的選擇；若完全不想碰程式，請直接看路線 D。ppt2video 很貼題，但因維護與輸入模式都不理想，不列為推薦方案。

路線 B：字幕自動對時與校正

這一類可讀取既有錄音，產出有時間碼的字幕。它不負責決定投影片翻頁，但非常適合作為影片合成之後的第二步。

Repo 功能與本案適合度 規模與活躍度（2026-08-16 查） 付費 API／本地性 非工程師友善度
openai/whisper 多語言語音辨識，可從錄音轉出逐字稿與段落時間碼，是字幕流程的基礎模型。可將使用者的講稿作為校稿參考。 約 10.7 萬 stars；2026-07-28 有 push，活躍。 MIT、模型可本地推論；下載模型後不必用付費 API。GPU 會明顯較快。 低：官方主要是程式／命令列。
m-bain/whisperX 在 Whisper 上加上詞級時間對齊與說話者分離；比一般段落時間碼更適合做逐字同步字幕。 約 2.4 萬 stars；2026-07-13 有 push，近期活躍。 BSD-2-Clause；辨識與對時可本地。使用說話者分離的附加模型時，可能需 Hugging Face 帳號／接受其模型條款，但不是付費 API 的必需條件。 低：Python／GPU 導向。
SubtitleEdit/subtitleedit 可視化建立、調整、轉換與燒錄字幕；支援本地或可選雲端的語音辨識，並能用波形精修時間。它是本案最值得非工程師優先試用的開源 GUI。 約 1.4 萬 stars；2026-08-16 有 push，活躍；2026 年的 v5 為跨平台版。 MIT；核心編輯、播放與本地功能可離線。若自行選用第三方雲端翻譯／STT，才會送出必要資料並受該服務計費／條款約束。 高：有 Windows、macOS、Linux 安裝包與圖形介面。

判讀：本案最實際的字幕組合是「Whisper 或 WhisperX 先出初稿 → Subtitle Edit 以講稿與波形做人工校對 → 將字幕掛入／燒入已完成的投影片影片」。即使講稿已經存在，也建議讓工具從真實錄音產生時間碼，因為人講話的停頓不會完全等同文字稿。

路線 C：投影片＋虛擬講者／數位人

這類工具只產出人物影片（或把人物嘴型對到音訊），還需要再用 FFmpeg、Remotion 或 GUI 剪輯器把人物放到投影片一角。請僅使用自己或取得明確同意的人像與聲音，並在課程發布情境中清楚標示合成內容。

KlingAIResearch/LivePortrait 將來源肖像／肖像影片套用「驅動影片」的表情與頭部動作。畫面品質與控制力佳，但不是直接用音訊驅動嘴型；需另備一段驅動影片，或與 lip-sync 工具串接。 約 1.9 萬 stars；2026-06-01 有 push，仍可視為近期維護。 MIT、可本地跑；模型下載與較好的 GPU 是實務門檻。 中低：有 Gradio 介面與 Windows 一鍵包的相關說明，但素材概念與安裝仍偏技術。

OpenTalker/SadTalker 一張肖像＋音訊即可產生說話頭像，輸入形狀最貼近本案。 約 1.4 萬 stars；最後 push 2024-06-26，並非 2026 仍活躍維護的首選。 README 說明為 Apache-2.0（附第三方例外）；可本地、需下載模型，通常需 GPU。商用前仍須逐一核對模型與第三方元件。 中低：有 Gradio WebUI／Windows 批次啟動，但舊版 Python/CUDA 相依容易卡住。
Rudrabha/Wav2Lip 將一段人臉影片與任意音訊對嘴，是經典參考實作；可把既有錄音接到講者影片。 約 1.3 萬 stars；最後 push 2025-06-22。仍有人使用，但不是最省心的 2026 新專案選擇。 開源版 README 明定只限個人／研究／非商業用途；本地可跑但商業課程不可直接採用，商用需另洽其服務。 低：Python／模型檔／GPU。

路線 D：免寫程式的 GUI／錄製與剪輯

3. 針對本案的具體推薦

推薦一：先做「投影片＋既有錄音＋字幕」，不要先上數位人

這是最適合目前素材、失敗成本最低的主線：

  1. 將投影片輸出為每頁圖片或靜態 PDF 頁面；若原檔依賴動畫，先用 PowerPoint／Keynote 輸出成影片，並接受它不再是可自由重排的單張圖。
  2. 建立切頁時間：最省事的是把錄音按投影片拆成多段；若只能提供一段長錄音，請在講稿標示「第幾頁從哪一句開始」，再人工檢查切頁。
  3. 非工程師優先使用 Kdenlive 或 Shotcut 將畫面和錄音放上時間軸；需要批量重複產片才請人以 FFmpeg／Remotion 做模板化。
  4. 以 Whisper／WhisperX 取得時間碼，再用 Subtitle Edit 開啟影片與講稿校對、匯出或燒入字幕。

理由：使用者已經錄好本人的聲音，真正有價值的是同步正確、聽得清楚、看得懂字幕；這條路不會為了不必要的 AI 語音／人像而把專案變成 GPU 與授權問題。

推薦二：若要講者感，優先拍「真人小窗」；虛擬人當第二階段實驗

只要用手機拍一段正面講者影片，再用 Kdenlive／Shotcut 或 OBS 做「投影片主畫面＋右下角真人小窗」，通常比單張照片生成數位人更自然、更可控。若確實不想露臉，才小規模測試 SadTalker 或 MuseTalk；若課程涉及商業用途，避開開源 Wav2Lip，並逐一重查模型與素材授權。

4. 已知限制與常見坑

  1. 一段長錄音沒有自動切頁的真實答案。 語音辨識可給「何時說了什麼」，卻不知道「哪一頁應出現什麼」；要靠頁碼標記、每頁音檔、或人工校點。
  2. 講稿不是錄音的時間碼。 即使文字完全一樣，語速、停頓、口誤與臨時補充都會讓字幕漂移；自動字幕必須至少人工抽查每頁起訖、專有名詞、中文斷行。
  3. 投影片動畫最容易丟失。 把 PPT/PDF 轉成圖片後，只剩靜態頁面。要保留逐項動畫、嵌入影片與特效，應先用原生 PowerPoint／Keynote 播放並輸出影片，或改成時間軸手動重建。
  4. 字幕可選「可切換」或「燒進畫面」。 SRT/VTT 可讓平台切換、修正容易；燒錄字幕最不會在播放器上跑版，卻不能再獨立關閉或改字。保留原始字幕檔是必要的。
  5. 多媒體授權不是只看 repo。 FFmpeg 的編碼選項、Remotion 的公司授權門檻、開源模型權重、訓練資料、字型、投影片圖片、背景音樂都可能各有條款。尤其 Wav2Lip 開源版明示不可商用。
  6. 數位人要有同意與揭露。 使用真人臉、聲音或影片時取得明確同意；不要用未授權肖像，也不要讓觀眾誤認合成畫面是實拍。
  7. 本地 AI 的成本是硬體與時間而非 API 帳單。 Whisper 小模型可用 CPU 但慢；高品質字幕、MuseTalk／SadTalker 多半需要可用的 NVIDIA GPU、模型下載空間與環境排錯時間。
  8. 先做 1–2 分鐘樣片。 先用 3–5 張投影片驗證畫面比例、字體、字幕位置、切頁點、音量與輸出品質，再批次完成整堂課；這比做完一小時才發現問題便宜得多。
