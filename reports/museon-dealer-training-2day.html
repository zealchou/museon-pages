00設計理念：為什麼這樣設計

這份課程不是「功能教學手冊」。它要解決的真問題是——客戶感受不到 Museon 跟 ChatGPT 的差別。差別不在功能清單，在經銷商能不能用顧問的姿態診斷、能不能把客戶的隱性知識做成 RAG、能不能在客戶端陪跑兩個月直到復能。三個來自真實資料的發現，定錨了整份設計：

真相一｜白老師案揭露「能力缺口」在哪。 從 5/26→6/21 的真實會議逐字稿看，經銷端做得最吃力的不是技術，是：算力/成本估不準、外部串接「不確定能不能做」、機房規劃現學現賣、中台價值講到客戶聽不懂、範圍一路膨脹收不住。這些踩坑，就是課程模組的來源。
真相二｜真實活躍客戶只有 5–8 人，不是「市場已驗證」。 skill 使用 log 1411 筆裡，最大兩個帳號是開發者本人（佔 ~19MB，斷崖第一二名）。這代表客戶端真實採用率還很低——這不是壞消息，是經銷商的機會缺口，課程要教的是「怎麼把睡著的能力喚醒給客戶」。
真相三｜最有差異化的功能，幾乎全在睡覺。 命理體驗類（人類圖/解夢/合盤）、整條媽媽市場產品線、短影音/storytelling/live-commentary——黏著度與裂變力最強，卻被點個位數次。這些是 Day1 下午的「差異化主菜」。

01經銷商能力模型（六大類）

以下六類從白老師案「服務這個客戶實際需要什麼」反推得出，每類都有逐字稿證據支撐。整份課表就是依這六類編排。

① 需求診斷與顧問能力
聽懂業態、窮舉複雜業務規則、不亂承諾、把痛點換算成省錢數字。
證據：Eric「我不能需求聽不清楚就跟你說可以」；折扣「3×3 就有九種可能性」。
② Museon 系統操作與配置
前中後台三分法、權限 min(Agent,員工)、ID 串接、記憶/結晶/RAG 配置、人格克隆。
證據：「前台都可換，資料統一被中台處理，AI 是中台」。
③ 技術導入與串接
後台/資料庫設計、舊資料遷移、外部串接、本地端機房/網路、算力壓測、AI 模組「人審最終」邊界。
證據：「同時 10 個人用就不 ok」；口說對打「會燒很快」。
④ 提案、報價與商業溝通
用 Museon 產結構化提案、模組化報價、多角色/隔代決策溝通、範圍收斂。
證據：「報告完全不用手做，跟 AI 聊天就出來」；達哥「越講越大，要收斂」。
⑤ 落地陪跑與專案管理
望聞問切式輔導、分階段上線、客戶端內訓、合規把關。目標是「你學會了，我就撤退」。
證據：「至少落地輔導兩個月，每週來一次」。
⑥ 差異化變現（課程加值）
把睡著的高黏著功能（命理/媽媽線/短影音/敘事）變成引流鉤子與裂變引擎。
來源：真實數據揭露這些「有料卻被冷落」。

家庭・媽媽市場（完整一條產品線，幾乎全冷）

mom-parenting-coach · meal-planner-mom · side-hustle-mom · child-dev-router · parent-child-sync-rescue · circle-amplifier

C附錄：資料清洗 → 結晶 → Wiki → RAG 操作步驟

Day2 模組 6 的教材。以下五階段每一步都對應 Museon 真實模組（已逐一驗證），經銷商在客戶端能照做。完整版見 docs/dealer_wiki_rag_pipeline_playbook.md。

0
抓取（識別可優化工作流）
三判準找客戶的可 SOP 化環節：重複性高、規則明確、依賴人腦。資料來源寫進 digest（pulse_engine._save_to_digest()），人手知識直接編輯 Wiki。
1
資料清洗
build_wiki_from_digest.py 把雜亂資料轉成標準 markdown（frontmatter 帶 crystal_status: pending）。客戶給的紙本/Excel/LINE 對話先整理成可結晶格式。
2
結晶（品質硬閘）
兩條路徑共用品質閘 atom_crystallizer.passes_crystal_template（擋太短/太長/低多樣性/樣板）。結晶 ≠ 筆記，差在這道硬閘 + 結構化欄位。經 crystallize_wiki_pending.py 寫入 crystal.db。
3
向量化進 RAG
父子雙層：WikiRagSync.sync() 索引細節（documents）、_vector_index() 索引摘要（crystals），靠 source_file 對齊。這一步才是「變成 RAG」。
4
調用與驗證
對話時經 vector_bridge.search() 撈回注入。三關驗證真的進去了：crystal.db → frontmatter → vector_bridge 反查。每日閉環由 launchd（5:30）跑 wiki_rag_sync_daily.py。

Claude Code / Cowork 的角色：Claude Code 直接跑這些 script（.venv/bin/python 可執行已實證），是經銷商在客戶端的「執行手」；Cowork 用於團隊協作場景（註：repo 內無對應程式碼，此為依產品定位的建議，非原始碼實證）。

資料限制誠實聲明（請先讀）

  • 「前 30 名使用者 × 各用哪些功能」無法精確算。skill_usage_log.jsonl 不含 user_id，所有 skill 次數都是全域加總，不是 per-user。任何「某使用者最常用 X」皆禁止捏造。
  • 「活躍約 5–8 人」是推斷，不是精確數。依據是記憶體積（du）＋群組訊息量兩個 proxy。
  • 高頻 ≠ 客戶愛用。TOP 流量被兩個開發者帳號嚴重污染，「內部 vs 客戶價值」的二分本身帶推斷成分。
  • 「白老師」是客戶（國際語言中心），不是講師。能力模型是從「服務此客戶所需」反推，非 Museon 官方經銷制度（分潤/層級/考核逐字稿無實證）。
  • RAG pipeline 兩處未實證：vita-explore cron 註冊點未在本次讀到的檔內出現；Claude Cowork repo 內無對應程式碼。
  • 白老師案截至 6/24 仍在「規劃費」階段，未見簽約。最終報價/上線時程未定。法規結論（吃藥提醒、薪資電子簽核留存）皆停在「要問人資顧問」，不可當定論。
