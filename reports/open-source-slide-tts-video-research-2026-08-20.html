開源方案調查：投影片＋TTS 旁白自動輸出 MP4

日期：2026-08-20（Asia/Taipei）
研究目的：替現有本地 Qwen3-TTS 聲音克隆管線，尋找「投影片畫面＋旁白時間軸 → MP4」的可用開源基底，而不是重新實作影音合成器。

先講結論：最適合直接接入的是 Editly。它能直接吃「圖片序列、整段 Qwen3-TTS WAV、每頁起訖秒數」，以每頁 clip 的 duration 加上全域 audioFilePath 輸出 MP4；所缺的僅是把既有時間表編譯成 JSON5。若改為「每頁一個 Qwen WAV」，可選 Montaigne 的純合成段，或直接使用 FFmpeg。沒有找到一套夠成熟、又能同時原生處理本地 Qwen3-TTS、中文句級對齊、HTML/PPTX/PDF 三種投影片輸入、及可驗證翻頁時間的完整專案。

1. 搜尋範圍與方法

問題拆解與判準

把需求拆成兩個不可混淆的層次：

  1. 時間軸產生：由逐字稿與 Qwen3-TTS 產物決定句子／頁面的起訖秒數。
  2. 畫面合成：依頁面起訖秒數顯示投影片，將旁白混入，輸出 H.264/AAC MP4。

本報告只把「實際能做第 2 層、或明確含第 1＋2 層」的專案列為候選。純 ASR、純字幕、純 TTS、只做 PPTX 產生而沒有影片輸出者均排除。

檢索方式

  • 使用的英文關鍵字（12 組組合）：PPTX TTS narration video generator open source、slides audio ffmpeg video、images audio duration ffmpeg slideshow、slide timing ffmpeg presentation video、Marp voiceover video、presentation PDF images audio video、PPTX Qwen TTS video export 等。
  • 來源：GitHub repository 搜尋結果與各 repository README／原始碼／安裝文件；GitHub REST API 的 pushed_at、stargazers_count、license 欄位；必要時再讀到實際的合成實作檔。
  • 約檢視 10 個 GitHub 倉庫，最後保留 7 個候選。每一個下列 GitHub 主網址均以 HTTP GET 驗證為 200（2026-08-20）；星數為同一時間點的 API 快照，會隨時間變動。

重要界線

「旁白時長驅動投影片」不等於「逐字稿自動得到可靠的中文句級／字級時間點」。多數候選只會：

  • 讀取現成音檔的 ffprobe 時長；或
  • 對每頁文字呼叫其指定 TTS，再以每頁音檔長度決定翻頁。

因此，若 Qwen3-TTS 一次產出整段旁白，仍要有一個時間表來源（例如逐句生成後累加時長、或以 ASR／forced alignment 對齊）。這是上游資料問題，不應藏進 MP4 合成器裡。

2. 候選方案清單

A. 輕量級：圖片序列＋音檔 → 影片

專案 GitHub、更新與熱度 實際能力與本案吻合度 授權與安裝複雜度
Editly mifi/editly；最後程式推送 2025-05-12；約 5.5k stars Node.js 的宣告式影音編排器，底層為 FFmpeg。每個 clips[] 可指定 duration、圖片 layer，頂層可指定整段 audioFilePath，也可加任意時間點音軌。直接符合：把頁面 end - start 填為每個 clip 時長、把全段 Qwen WAV 放入 audioFilePath 即可輸出 MP4。須自行檢查「最後頁 end ≈ 音檔時長」；它不會產生逐字稿時間點。 MIT。需 Node.js、FFmpeg 與 FFprobe；Linux 可能要補 headless-gl 系統相依。無 GPU、無雲端服務需求。最適合做正式合成層。
videoshow h2non/videoshow；最後程式推送 2026-01-21；約 900 stars Node.js 封裝 FFmpeg 的圖片 slideshow 工具，支援一段音檔、每張圖片物件的 loop 秒數、轉場與字幕。直接符合核心輸入：圖片物件的 loop 可由每頁起訖秒數換算，.audio() 可放全段 Qwen 音檔。比 Editly 簡單，但排版／合成控制較少，且 README 要求圖片同尺寸。 MIT。需 Node.js、FFmpeg；若要字幕／MP3 功能，FFmpeg 需含 libass、libmp3lame。無 GPU、無雲端。適合快速 MVP。
FFmpeg Video Slideshow Scripts tanersener/ffmpeg-video-slideshow-scripts；最後程式推送 2023-07-16；約 500 stars Bash 範本集合，提供圖片／影片序列、畫面停留秒數、轉場與輸出 H.264。部分符合：可當視覺軌模板，但原設計不是「單一旁白＋每頁時間表」的完整介面，需補一個 FFmpeg 音訊 mux 與依頁時長產生設定的薄包裝。適合想完全掌控 filter graph，而非直接導入的情況。 MIT（倉庫主程式）；注意示例素材／少數附帶資產另有授權，產品僅應使用自己的投影片與音檔。純 Bash＋FFmpeg，無 GPU、無雲端。

A 類判讀

三者都不處理「句子時間點怎麼來」，但這反而吻合本案：Qwen3-TTS 已在本地，時間表可以是本管線的明確契約，而不必被另一套雲端 TTS 綁死。成熟度與可維護性排序為 Editly > videoshow > Bash 範本。

B. 較完整的「簡報／講者 → 有旁白影片」端到端專案

專案 GitHub、更新與熱度 實際能力與本案吻合度 授權與安裝複雜度
PPT Master hugohe3/ppt-master；最後程式推送 2026-08-19；約 48k stars 能從講者備註產生逐頁旁白，並把音檔嵌回 PPTX；文件列有 Qwen TTS backend，也提供現成每頁音檔目錄的 --recorded-narration audio。可利用 PowerPoint 的原生影片輸出保留轉場／物件動畫。部分符合：若輸入是 PPTX 且可把 Qwen 音檔按頁命名，適合；但不是「圖片序列＋整段音檔＋外部起訖秒數」直入。其 Qwen 路徑指向 DashScope 的雲端 API，不是現有本地 Qwen3-TTS。 MIT。基礎需 Python 3.10+；原生 MP4 匯出另要求 Windows PowerPoint 2016+。內建 TTS 可能需要雲端 API；若只餵既有逐頁音檔則不需 GPU／雲端，但仍受 Windows PowerPoint 限制。
Montaigne yanndebray/montaigne；最後程式推送 2026-03-02；約 2 stars Python 工具鏈可由 PDF／PPTX 抽頁、產生講稿／TTS，並有 essai video --images slides/ --audio audio/。其 video.py 確實以 page_*.png 配對 slide_*.wav/mp3，用 FFprobe 取得每頁音檔實際時長後各自成片再 concat。接近直接符合：將 Qwen 每頁輸出命名為該規格即可；但不吃「一段總音檔＋頁面 start/end」，也未見句級對齊與圖片／音檔數量不一致的硬失敗檢查（以較短一側為準）。 MIT。需 Python 3.10+、FFmpeg；完整腳本／翻譯預設用 Gemini，TTS 可用 Gemini／ElevenLabs，另有 Coqui 本地選項（後者才可能需要 GPU）。用它的純影片函式加 Qwen 音檔不需雲端。成熟度低，先做 smoke test。
videoascode grokify/videoascode；最後程式推送 2026-08-13；約 3 stars Go 工具將 Marp Markdown、旁白和 FFmpeg 合成影片：逐頁錄製並以音檔時長決定畫面時長，最後 concat。vac slides video --manifest ... 可跳過 TTS、讀預先生成的音訊 manifest。需簡單改接：要把 Qwen 逐頁音檔與 metadata 轉成它期待的 manifest；投影片原生輸入限 Marp Markdown，不是既有 PPTX／PDF。 MIT。需 Go 建置、FFmpeg、Marp CLI；實作路徑還會用瀏覽器錄製（macOS 可能需螢幕錄製權限）。內建 TTS 是 ElevenLabs，使用預先音訊 manifest 後可不呼叫雲端；無 GPU。
slidemovie sekika/slidemovie；最後程式推送 2026-07-11；約 1 star Markdown 寫投影片與 notes 旁白，轉 PPTX、渲染投影片、TTS、再輸出 MP4；也有 incremental build。部分符合：很適合從零做 Markdown 課程，但公開文件只描述由其 multiai-tts 產音，未找到可直接餵本地既有 Qwen WAV＋外部頁面時間表的入口；替換 TTS 層才可接入。 MIT。需 Python、FFmpeg、Pandoc、LibreOffice、Poppler、ImageMagick；預設 TTS 需 Google／OpenAI／Azure API，或本地 VOICEVOX 服務。無 GPU 是可行的，但依賴較多且專案尚新。

B 類判讀

  • 若成品要保留 PowerPoint 原生動畫／轉場，而且可在 Windows PowerPoint 匯出，PPT Master 是唯一具明確原生 PPTX 音訊／影片流程、且社群規模明顯較大的候選。
  • 若成品本質上是「每頁靜態投影片＋旁白」，Montaigne 與 videoascode 都不值得取代 Editly：前者可借用逐頁音檔慣例，後者還引入 Marp 與瀏覽器錄製。
  • 這一類專案整體都很新（除 PPT Master 外），不應把它們當作本地生產依賴而不先跑一份 3–5 頁代表投影片。

3. 與既有 Qwen3-TTS 管線的接法與明確推薦

推薦一：正式主路徑 — Qwen3-TTS + Editly

推薦度：最高。 原因不是它「最像 AI」，而是資料契約剛好吻合，而且避免再引入第二個 TTS 供應商。

輸入契約可固定為：

{
  "audio": "audio/narration.wav",
  "slides": [
    {"image": "slides/001.png", "start": 0.0, "end": 28.42},
    {"image": "slides/002.png", "start": 28.42, "end": 61.08}
  ]
}

薄轉接層只負責：

  1. 驗證頁面排序、start < end、相鄰頁面不重疊／不留未宣告空洞。
  2. 驗證最後一頁 end 與 ffprobe(narration.wav) 時長在容許誤差內。
  3. 輸出 Editly JSON5：每頁一個 image clip，duration = end - start，全域 audioFilePath 指向 Qwen WAV。
  4. 交給 Editly／FFmpeg 編碼 MP4，再以 FFprobe 回讀總時長、影像／音訊 stream 與解析度。

這不是重寫合成器；只是把已算好的時間表翻譯成成熟編排器的設定。它支援 HTML 投影片時，只要先以 Chromium／Playwright 依固定 viewport 截成 PNG；PPTX／PDF 則先渲染成同一份有序圖片序列。三種來源到合成層的資料型別因此一致。

推薦二：有逐頁 Qwen 音檔時 — Montaigne 的純影片段或直接 FFmpeg

若 Qwen3-TTS 本來就是每頁或每句個別輸出，將每頁音檔合併為該頁 WAV，再依 page_001.png／slide_01.wav 的規格使用 Montaigne 的 generate_video()，可省掉建立 Editly 設定。不過應先補兩道外部驗證：圖片數量＝音檔數量、依檔名索引一對一配對；因為原實作以排序後的最短列表處理，少檔可能被靜默截斷。

若只需要靜態投影片、無轉場與複雜 overlay，直接使用 FFmpeg 亦可；但建議將命令生成、輸入驗證與輸出 probe 留成可測試的小工具，而不是在 shell 裡散落拼字串。

有條件選項：PPT Master

僅在下列條件都成立時採用：既有來源主要是 PPTX、必須保留原生轉場／物件動畫、可提供 Windows + PowerPoint，且能將本地 Qwen 音檔整理為每頁音檔目錄。否則它的 PowerPoint 與雲端 Qwen API 假設，會讓目前 Linux／本地 Qwen3-TTS 管線變複雜。

沒有找到的部分（誠實邊界）

在本次約 12 組關鍵字、10 個 GitHub 倉庫的搜尋範圍內，沒有找到成熟且可直接使用的開源專案，同時滿足以下四項：

  1. 原生支援本地 Qwen3-TTS 聲音克隆；
  2. 自動產生可審計的繁中句級／字級時間戳；
  3. 直接接受 HTML、PPTX、PDF 三種既有投影片；
  4. 以外部逐頁起訖秒數、單段旁白產出影片，且對長度不一致有硬性驗證。

相關搜尋字包括 Qwen TTS PPTX video export、slides audio ffmpeg video、PPTX TTS narration video generator open source、Marp voiceover video。這不是「沒有任何工具」，而是現有工具通常只覆蓋合成，或綁定自己的雲端 TTS／投影片格式。最小、可控的缺口是時間表／manifest 轉接與驗證，不是另造一套影片引擎。
