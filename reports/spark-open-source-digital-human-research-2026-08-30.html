MUSEON｜技術選型查證

Spark 上的開源「克隆數字人」

面向繁中講課影片：克隆聲音生成旁白，真人樣貌的人像隨音訊對嘴、帶基本頭部與表情動作；同時判斷是否值得為未來短劇保留延展性。

查詢日期：2026-08-30（Asia/Taipei）。本報告只讀取公開網頁、GitHub API 與這台機器既有的只讀實測紀錄；未安裝套件、未下載權重、未執行候選模型、未寫任何程式。

結論先講：Qwen3‑TTS 是 Spark 上暫定的聲音首選——它是唯一已在本機 GB10／ARM64 以 GPU 完成真人 clone 的候選。影像端不應現在鎖定唯一方案：MuseTalk 1.5 是「已有本人模板影片、只需穩定對嘴」的低資源 PoC 候選；EchoMimic V3 Flash 才是「一張人像＋音訊，同時帶嘴形、頭部／表情（可到半身）」的直接候補。兩者都沒有官方 Spark／ARM64 支援，必須先各做獨立試片，不能把第三方成功貼文當作保證。

這改正了一個關鍵誤判：MuseTalk 是 lip-sync，不會單靠音訊替靜態照片生成可信的頭動與表情；若現階段可先拍一段有自然頭動的本人影片，它仍是最務實的講課路徑。

1. 問題邊界與硬體判準

事實對選型的意思
GB10、sm_121、aarch64、119 GiB 統一記憶體不能把 x86_64 CUDA wheel／Docker image 當成可用；CPU 與 GPU 共用記憶體，OOM 可能讓整機卡住。常態可即時使用只有約 12–27 GiB。
其他 LLM 常駐約占 91 GiB先選「推論可在 4–18 GiB 等級試片」的方案；不能預設可拿 100 GiB 做全模型微調。訓練要先協調停掉常駐模型。
繁體中文為主、商業教育內容「支援 Chinese」不等於保證台灣繁中自然；需以人名、地名、數字、英中夾雜做聽感驗收。程式碼 MIT/Apache 也不自動替第三方 checkpoint、InsightFace 模型或訓練資料取得商用權。
既有實測本機 torch 2.9.0+cu130／ARM64 已成功跑 Qwen3‑TTS 真人 clone、輸出 24 kHz WAV；這是唯一可直接視為 Spark 已驗證的候選元件。
本題的「微調」有兩種完全不同的事：多數 talking-head 專案只要一張照片或一段影片就能把指定人像放進推論，這是推論時身份條件，不是把這個人訓練進模型。真正微調需要成批、已取得肖像與聲音授權的影片。現階段講課影片不應先做後者；先做 30–60 秒試片。下表若官方未公布最小資料量／訓練時數，一律寫「未公布」，不以社群傳言補數字。

4. 推薦組合與實際工作流

建議不是一條盲選線，而是「已驗證聲音＋二選一影像試片」：

  1. 聲音（先固定）：沿用 Qwen3‑TTS，使用本人（或獲明確書面授權的講師）30–90 秒乾淨、無背景音的繁中錄音與正確逐字稿建立 clone prompt；每頁／每句產生 WAV，延續現有聽寫稽核與發音詞典。它的 zero-shot clone 已可用；全參數 SFT 雖有官方碼，Blackwell FlashAttention 2 與記憶體需求未驗，不排入第一階段。
  2. 影像 A（若可拍模板影片）：拍 25 fps、正面、光線固定的本人影片，先 15–30 秒試片、正式可拍 2–5 分鐘以取得自然待機頭動；用 MuseTalk 只改嘴形。這是最低風險的「講者小窗」作法，因頭部／表情來自真人素材，不是模型憑音訊猜。不要計畫在現有 12–27 GiB 餘額微調它：官方 config 的訓練 stage1／stage2 分別約需 32／54 GiB。
  3. 影像 B（若必須單張照音訊帶動）：以 EchoMimic V3 Flash 做同一段 30–60 秒繁中試片。它更符合題目要的 audio-driven movement，但 12 GiB 官方下限幾乎吃掉 Spark 的常態餘額，且 ARM 全未驗；未過相容性與人眼 QC，不能進批量製作。
  4. 合成：既有投影片影片為主畫面，數位人只作右下角或章節開場的小窗；兩路均先驗 30–60 秒繁中段落，再選一路長片批次。這比全螢幕擬真人像更能控制低解析嘴區與偶發抖動。
驗收閘門（尚未執行）可接受條件為何重要
ARM 安裝／載入在獨立 venv、未動現有 Qwen TTS 下，MuseTalk 能載入並產出 10 秒無錯 MP4。直接驗證 Python wheel、TensorFlow、Torch、CUDA 13／sm_121，不用猜。
記憶體LLM 常駐不動時，30–60 秒試片不讓可用統一記憶體跌到危險值；若需要暫停 LLM，明確協調後才做。GB10 沒有「爆掉某張卡就算了」的獨立顯存緩衝。
繁中品質人名、台灣地名、數字／單位、英文術語四類各抽樣；人耳確認聲音，畫面逐格看嘴形、牙齒、抖動。模型聲稱 Chinese 並不能保證繁中講課可交付。
授權保存本人肖像／聲音同意、每個 checkpoint model card、替代 detector 的 licence notice。MIT／Apache repo 的商用結論不涵蓋所有 weights／人臉模型。

5. ARM64 風險與退路

最大風險不是 GB10 算力不夠，而是舊的 x86 CUDA 軟體棧。MuseTalk 另有 mmcv／mmpose CUDA op 與 amd64 ffmpeg 假設；LivePortrait、Hallo、JoyVASA、LatentSync 都明確釘住某版 onnxruntime-gpu、InsightFace 或 xformers；許多對應版本沒有 Linux aarch64 CUDA wheel。EchoMimic V3 雖較新，仍含 TensorFlow／ONNX／video diffusion 的 ARM 空白。Hallo3／CosyVoice 訓練另有 DeepSpeed／Triton 編譯風險。Spark 上現有 Qwen 推論已證明「現代 PyTorch CUDA 13 ARM」可行，不能反推 2024 CUDA 12.1 pin 都可用。

  • MuseTalk A 路的工作量：估 2–5 個工程日完成隔離環境、ARM wheel／MMCV/MMPose source build、版本問題排查與一段試片；這是排錯預算，不是保證。若兩次同型編譯／ABI 失敗，停止盲試、回查上游或換路。
  • EchoMimic B 路的工作量：估 2–5 個工程日，重點是 TensorFlow／ONNX／Wan stack 的 ARM 適配與 16 GiB 記憶體守門；它較直接，但不是較安全。
  • 若兩路均被 ARM 阻擋：不要硬把 x86 Docker 跑在 ARM 模擬層；以現有 Qwen3‑TTS＋實拍本人小窗作講課第一版，數位人等有 ARM 原生影像棧或另備 x86 NVIDIA worker 再開。這不是降低品質的偷懶，而是避免為未知依賴犧牲 Spark 的常駐服務。

6. 能否延伸到短影音／短劇？

結論：大部分是另一條技術棧，不是把講課頭像「加碼」即可。Qwen3‑TTS 可沿用作角色聲音；人像 identity 資料、同意與發音詞典也可沿用。但 MuseTalk／LatentSync 的任務是「已有影片的臉部嘴形重定時」，LivePortrait 是「把驅動動作轉給一張人像」；它們不解決多鏡頭、全身、手部、服裝／背景／道具一致性、角色互動、場景連續性、鏡頭語言與長片 temporal consistency。

Hallo3、EchoMimic V3 雖向半身／動態場景靠近，仍不代表可可靠地做短劇，且對 Spark 現有 12–27 GiB 空檔與 ARM 相容性更不利。短劇要重新評估「可商用的 image/video foundation model＋角色 LoRA／reference control＋鏡頭級生成／重繪＋剪輯與一致性 QA」；這是新專案。現階段的講課方案應刻意採小窗／固定鏡位，能保留人物可信度，卻不假裝已解決場景級影片生成。
