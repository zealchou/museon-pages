Hermes Desktop「HUD Mode」查證

研究日期：2026-08-25（Asia/Taipei）｜範圍：官方來源、官方 GitHub、官方技術文件
一句話結論：消息的核心為真，但「任何全螢幕遊戲、包括 WoW，都可直接疊加並看懂／操作」是過度延伸。Nous Research 的官方 repo 已有 Hermes Desktop 與 HUD mode；HUD 是 Electron 的透明、無框、always-on-top 聊天視窗。它可覆蓋一般視窗、borderless fullscreen 與 macOS fullscreen Spaces；官方原始碼卻明示，真正的 exclusive fullscreen 會繞過 compositor，HUD 無法覆蓋。HUD 本身也不會自動讀取底下畫面的像素；看圖與操作是另行啟用的 Computer Use（cua-driver）能力。

1. 產品與 HUD Mode 是否屬實

結論Hermes Desktop 確為 Nous Research 官方產品；HUD mode 確實已存在於官方主線原始碼。

依據來源NousResearch/hermes-agent 的 Desktop README將它定義為 Hermes Agent 的原生桌面 app，支援 macOS、Windows、Linux；官方文件也提供 Desktop 下載入口。HUD 的專用程式碼於官方 repo 的 2026-08-24「HUD game-overlay mode」提交加入，且目前主線含 HUD 視窗、遊戲偵測與輸入策略。

技術細節或限制HUD 不是把網頁浮在應用內，而是獨立 Electron BrowserWindow：官方程式描述為「transparent, frameless, always-on-top」的完整聊天 renderer，使用相同的 Hermes composer／session，不是簡化的假面板。它可在別的 app 上方打字、收回覆，閒置時採 click-through，讓點擊穿透到底下 app。見HUD state 原始碼與平台輸入策略。

結論「最近加入」可成立於主線開發，但尚不能等同於「每個正式安裝包都已有」。

依據來源HUD game-overlay 的官方提交日期是 2026-08-24；官方 GitHub releases 清單的最新 tagged release 是 2026-08-21 的 v2026.8.19，早於該提交。

技術細節或限制因此可嚴格確認「官方主線已有」；但此查證沒有找到含 HUD 的 release note、已簽名 installer 或 WoW 實機影片。若 Desktop 的內建 update 是從主線重建，使用者可能較早取得；是否已推進各平台正式 installer，查無明確依據。

2. 全螢幕遊戲與 WoW 說法

結論對「borderless fullscreen」可合理預期可用；對真正 exclusive fullscreen 則官方原始碼明說不能覆蓋。

依據來源hud-game-overlay.ts 的註解直接區分：always-on-top 視窗可蓋住 borderless fullscreen（現代遊戲常用）與 macOS fullscreen Spaces；但 true exclusive-fullscreen 會完全繞過 compositor，除非注入遊戲的 render pipeline，否則無法繪製在上方。該模組只每 1.5 秒枚舉視窗與螢幕邊界，偵測滿版 app 後調整 HUD 成低干擾、可瞥讀的遊戲樣式。

技術細節或限制這不是 Discord 那種把 DLL／render hook 注入遊戲的 native in-game overlay；它是作業系統 compositor 層的一般 topmost window。遊戲切成 exclusive mode 時，偵測仍可能知道有滿版視窗，但 HUD 會在後面，直到 alt-tab 令遊戲回到 composited output。Linux 亦有顯著限制：純 Wayland 可能不允許列舉其他視窗，官方程式會停用該偵測而非假裝成功。

結論「World of Warcraft 已被 Hermes 官方驗證能用」：查無明確依據。

依據來源本次檢索 Nous 官方網站、官方 repo（含 HUD 提交與原始碼）、官方 release，以及可追溯技術文件，未找到「World of Warcraft」的官方提及、相容性矩陣或實測證據。原始碼測試以 Balatro 作為一般滿版遊戲的模擬名稱，並非 WoW 實測。

技術細節或限制WoW 使用何種 fullscreen 模式、作業系統、顯示器與反作弊環境都會改變結果。可說的是：若它在目標機器以 borderless fullscreen 由 compositor 顯示，Hermes 的設計目標涵蓋此類情境；若為 true exclusive fullscreen，官方程式碼的限制直接否定覆蓋承諾。也查無官方依據可證明 Hermes 對 WoW 的輸入注入／反作弊相容性。

3. 它怎麼「看到」與「互動」

結論HUD 的「底下視窗」感知預設是視窗中繼資料，不是自動截圖或持續電腦視覺。

依據來源官方的 read_window_below tool 與 window-below 實作明寫只回傳 app 名稱、視窗標題、bounds、id 等 metadata，「never captures pixels or content」。macOS 若未授予 Screen Recording，標題也可能被隱藏；Wayland 的列舉能力會受限。

技術細節或限制所以「HUD 的位置就是上下文」的可靠解讀是：Agent 可知道哪一個視窗在 HUD 正下方，並非 HUD 自動把它變成視覺 token。這個設計是隱私／成本較輕的上下文提示，但不等於螢幕理解。

結論真正看像素、OCR／視覺推理與控制，是可選的 Computer Use 工具鏈；不是 HUD 專屬能力。

依據來源Nous 的官方 Computer Use 文件說明：Hermes 以 MCP over stdio 呼叫開源 cua-driver；capture 取得 screenshot（可含 Set-of-Marks 元素標記），畫面以 image parts 傳給具視覺能力的模型。文件也明說文字模型只能降級走 accessibility tree，並非 OCR／CV 的替代品。

技術細節或限制它是按需 capture，而非文件所證實的 HUD 持續錄影或持續 OCR。實務上可將「HUD 對話」和「要求 agent capture 目前 app」組合，但不應把這種可選、按需的流程描述為 HUD 自動看懂遊戲。

結論Hermes 可寫入互動，但需啟用 Computer Use，且預設行為有核准與平台限制。

依據來源同一份官方文件列出：macOS 使用 AX／SkyLight 與 pid-scoped event dispatch；Windows 使用 UIAutomation 加 SendInput／PostMessage；Linux 使用 AT-SPI 加 XTest 或 virtual keyboard。click、type、drag、scroll、key 等破壞性動作需要核准，除非使用者明確採用較高權限模式。

技術細節或限制這不是「只讀」產品。對自訂渲染或遊戲，accessibility tree 常稀疏／空白，官方建議退回像素座標，或乾脆跳過。Windows 管理員權限視窗受 UIPI 阻擋；Linux 純 Wayland 的 capture 需要 XWayland bridge；macOS 需要 Accessibility 與 Screen Recording 權限。這些都表示它不是全遊戲、全平台的無條件操控保證。

4. 授權與商用參考

結論Hermes Agent（含官方 repo 中的 Desktop／HUD 原始碼）是公開、MIT 授權；可商用採用或改作技術參考，但要保留授權與另行審核相依套件。

依據來源官方 repo 的 LICENSE 是 MIT License，GitHub repo metadata 亦標為 MIT 且 public。MIT 條文准許使用、複製、修改、合併、發布、再授權與販售，條件是所有副本或實質部分須保留 copyright 與 permission notice。

技術細節或限制因此 MuseGrade 可合法參考架構，甚至 fork／納入有適當 notice 的程式碼；但「Hermes repo 是 MIT」不自動讓每一個執行期依賴、模型、遊戲條款或平台私有 API 都無限制商用。尤其 Computer Use 另依賴 cua-driver，應按其 專案與版本的 LICENSE／相依清單做獨立 SBOM 與法務檢查。這是工程與授權範圍提醒，不是法律意見。

5. 同類產品／專案比較

產品／專案與 Hermes 的相似點關鍵差異與可查證限制
Cua Driver可讀螢幕像素＋accessibility tree、背景點擊／輸入，支援 macOS、Windows、Linux；正是 Hermes Computer Use 的底層。它是 driver／MCP 基礎設施，不是完整的浮動聊天 HUD。Windows 文件明示可用透明、click-through synthetic cursor overlay，展示「感知、控制、視覺提示」可拆成三層。
NVIDIA Project G-Assist可由 NVIDIA app overlay 或 Alt+G 在遊戲情境叫出；使用本機 RTX GPU 上的模型，面向遊戲與系統即時協助。NVIDIA 官方目前列出的主要能力是效能／圖形／系統設定、診斷與外掛控制，而非任意 app 的通用螢幕 agent。官方頁面沒有支持「它可看任意遊戲畫面並透過 UI 自動操作」的明確敘述。
Microsoft UFO²Windows desktop agent，混合 UIA、Win32、WinCOM、視覺 control detection，並在需要時選 GUI 點擊或 native API。它的官方說法是 sandboxed virtual desktop 的 Picture-in-Picture（仍標示 coming soon），不是在使用者現有桌面上的常駐聊天 overlay。強項是可靠 desktop automation，不是遊戲 HUD。

比較結論：Hermes 並非唯一擁有「AI＋螢幕／桌面互動」技術者。其有辨識度的組合，是把一般 OS-level floating chat HUD、窗口 metadata context，以及可選 cua-driver computer use 放在同一桌面產品。就遊戲原生 overlay／exclusive fullscreen 而言，它反而沒有採用 Discord／NVIDIA 類 render-pipeline 路線。

6. 對 MuseGrade 的直白判斷

有參考價值，但不能把它當作「已解決全螢幕遊戲 AI 視覺互動」的範例。

  • 值得借鏡：把「浮動對話面板」與「畫面感知／輸入控制」分層。HUD 可輕量、可 click-through、只帶 window metadata；只有在使用者問到畫面、明確要求操作時，才取得 screenshot 與走 computer-use approval。這降低長時間錄屏的隱私、GPU、token 與誤操作風險。
  • 必須產品化的邊界：MuseGrade 應明確把每次畫面讀取、保留時間、模型傳送位置、可否寫入、每一步是否核准，呈現為可理解的狀態，而不能以「HUD 浮在上面」暗示它已看懂全部。
  • 不可照抄的承諾：若產品主張涵蓋 WoW 或其他遊戲，必須另做「OS × GPU × fullscreen mode × anti-cheat × input mode」相容性矩陣與實機驗收。一般 Electron topmost window 不是 exclusive-fullscreen overlay 解法；若真的要覆蓋該模式，會進入 render hook／遊戲整合與反作弊風險，不能由 Hermes 的現有實作推論已可行。
研究方法：優先採 Nous 官方網站、NousResearch 官方 GitHub、官方原始碼與官方 release；比較對象採其官方網站／官方 GitHub。社群貼文未作為結論依據。
未證實項目：WoW 已實測相容、HUD 已納入所有正式 installer、HUD 自動持續看畫面、對 WoW 反作弊安全。上述皆未以「可能」填補，而是標為查無明確依據。
