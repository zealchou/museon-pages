DGX Spark（GB10）微調：NVIDIA 官方資料查證

查證日期：2026-08-30（Asia/Taipei）｜只採 NVIDIA 一手來源｜未安裝、下載模型或執行訓練

1. 結論

NVIDIA 所稱的 DGX Spark 微調，是從預訓練模型出發，以你的資料做 full SFT 或 LoRA／QLoRA／PEFT，讓模型適應特定領域、格式、行為或風格；不是量化。官方已有 NeMo AutoModel 與 PyTorch + PEFT 的 Spark Playbooks，並推薦 Unsloth。既有 ModelOpt 主要是 PTQ/NVFP4；同套件可做 QAT/蒸餾，但不是一般 SFT/LoRA 的預設工具。

NVIDIA 產品頁明示可微調至 70B；官方可操作案例則是 3B full SFT、8B full SFT／LoRA，以及 70B QLoRA。最穩妥的首步是依 NeMo recipe 用 20 steps、短 context、小 batch 驗證資料與訓練管線，而非直接長跑。

官方來源原文短摘可確定的意思
DGX Spark 產品頁“Fine-tune AI models up to 70 billion parameters.”產品行銷明示 70B 微調主張，並連到 128 GB 統一記憶體。

NVIDIA Gemma 4 文章“supervised fine-tuning and LoRA techniques”明確指向 NeMo AutoModel 從 Hugging Face checkpoint 做 SFT/LoRA。

Build 網站把 fine tuning（NeMo、PyTorch、Unsloth）和「以 Model Optimizer 量化 NVFP4」列在不同類別；這與 ModelOpt 官方總覽的 PTQ/QAT／Distillation 分類一致。

3. 推薦工具鏈

工具NVIDIA 官方對 Spark 的實際定位角色
NeMo AutoModelDGX Spark NeMo Playbook直接提供 full SFT、LoRA、QLoRA。首選起點；LLM/VLM，ARM64/Blackwell recipe，使用 nemo-automodel 容器。
PyTorch + HF PEFT/TRL/bitsandbytes官方 Playbook要求安裝這些套件，並提供 3B full、8B LoRA、70B QLoRA。PEFT 是外部開源套件，但被 NVIDIA Spark 教學明確採用；適合直接掌控 Python 訓練碼。
UnslothNVIDIA 官方部落格推薦並連到 DGX Spark 指南。第三方、較低記憶體的 fine-tuning framework。
ModelOpt官方 QAT 範例以 mtq.quantize 後接一般訓練，或用 QATSFTTrainer。與 PTQ/NVFP4 是同一 Python 套件、不同訓練功能；可做 QAT／蒸餾，但不是一般 SFT/LoRA 必要項。

精確區分：PTQ 是訓練後壓縮；QAT 讓量化誤差進入訓練以恢復精度；蒸餾是教師訓練學生。ModelOpt 的 20B full-QAT 官方例子需要 8×80 GB GPU，不能照抄到單台 Spark。

4. 實際流程與門檻

  1. 選 full SFT、LoRA 或 QLoRA。NVIDIA 對入門資料量的建議：PEFT 100–1,000 對，full fine-tuning 1,000+ 對；它不是品質保證。
  2. 整理資料。官方 PyTorch 範例採 instruction／input／output，串為一個 text 欄位，預設 512 samples；並沒有 Spark 專用的唯一 JSON 格式。
  3. 準備 CUDA 12+、Python 3.10+、Docker，並取得受限權重的 Hugging Face token／授權。NeMo Playbook 最低列 32 GB system RAM；Spark 實際為 128 GB UMA。
  4. 以 YAML recipe 載入基座 checkpoint，先用官方的短跑參數：20 steps、packed sequence 1024；70B QLoRA 用 micro-batch 1。
  5. 檢查 checkpoint 的 model、optimizer、dataloader 等產物，再以目標任務的保留測資評估。官方頁有 checkpoint 檢查，但沒有通用資料切分／品質門檻。

時間與記憶體：NeMo Playbook 的 setup + initial run 為 45–90 分鐘，PyTorch 為 30–45 分鐘，實際訓練依模型而變。官方效能文章的正文與表格 tokens/s 相差約 6–7 倍且未解釋，故不應拿它換算本機工時。

5. 這台機器的可行性

規模／方法官方 Spark 證據保守解讀
3B full SFT技術部落格 benchmark已有單 Spark full fine-tuning 案例。
8B full SFTNeMo 的 Qwen3-8B、batch 1、1024、20-step recipe最適合首個端到端 smoke test。
8B LoRANeMo recipe + benchmark官方直接支持，較 full SFT 輕量。
70B QLoRA產品頁、NeMo recipe、benchmark70B 主張對應 QLoRA，不是 70B full fine-tuning。
27B／35B LoRA沒有同架構、同設定的官方 Spark recipe值得驗證，但不是官方保證；需從小 batch、短 context、少 steps 實測。

你報告的 119.7 GiB 是名目 128 GB UMA 的實際可用值。官方沒有針對這個值公布各模型的安全餘量；CPU/GPU 共用池會受權重載入、資料、cache 與背景程式影響。

6. 沒查到的部分

  • Qwen3.8-27B、Ornith 35B 或目前實際 checkpoint 的官方 Spark recipe、batch、峰值記憶體、tokens/s、總工時。
  • 單 Spark 70B full fine-tuning 案例；官方 70B 示範是 QLoRA。
  • 官方通用的品質保證資料量、資料切分策略、過擬合門檻或訓練 SLA。
  • 專為單台 GB10 的 ModelOpt LLM QAT／distillation 教學；相反地，GPT-OSS 20B full-QAT 範例需 8×80 GB。
  • 「NVFP4/PTQ checkpoint 可直接沿用 PTQ 流程做泛用微調」的官方承諾。
